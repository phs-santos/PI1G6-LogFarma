# Um `.env` só para o desenvolvimento

- **Implementado em:** 2026-11-04
- **Última alteração:** —
- **Requisitos:** —

## Em poucas palavras

Antes havia duas cadernetas de senhas para o mesmo banco: uma do backend (`apps/backend/.env`) e outra do Docker (`infra/.env`). Se alguém trocava a senha em uma e esquecia a outra, o backend não conectava. Agora há uma caderneta só, na raiz do monorepo, e o backend e o Docker leem dela.

## O que

- Novo `.env.example` na raiz, juntando as variáveis do backend e as do banco do `infra/compose.yaml`.
- Removidos `apps/backend/.env.example` e `infra/.env.example`.
- Scripts do backend (`dev`, `db:migrate`, `db:seed`, `db:catalog`) leem `../../.env` (a raiz).
- `pnpm docker:dev` passa `--env-file .env` ao compose quando o arquivo existe.
- `infra/scripts/setup-dev.sh` cria o `.env` da raiz; se achar o `apps/backend/.env` antigo e a raiz ainda não tiver um, move ele para lá; avisa se sobrou algum `.env` antigo.

## Por que

As credenciais do banco de dev ficavam repetidas em dois arquivos (`DATABASE_URL` num, `POSTGRES_*` no outro), e era fácil um ficar diferente do outro. Com um arquivo só, há um lugar para conferir e para ensinar a quem chega.

## Onde

- `.env.example` (raiz)
- `apps/backend/package.json`, `apps/backend/src/env.ts`
- `package.json` (raiz) — script `docker:dev`
- `infra/compose.yaml` (comentário), `infra/scripts/setup-dev.sh`, `infra/README.md`
- `README.md`, `apps/backend/README.md`, `apps/backend/CLAUDE.md`, `apps/backend/AGENTS.md`

## Escolhas feitas

| Escolha                                            | Alternativas consideradas                             | Motivo                                                                                                          |
| -------------------------------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Só o dev usa o `.env` da raiz                      | Juntar também o de produção                           | Produção roda na VPS, com outras senhas, a partir de `infra/.env.prod.example`; misturar seria arriscado        |
| `--env-file .env` só se o arquivo existir          | Sempre passar `--env-file`                            | O compose dá erro se o arquivo não existe, e o `pnpm docker:dev` precisa funcionar sem `.env` (tudo tem padrão) |
| Backend lê `../../.env` com `--env-file-if-exists` | Biblioteca `dotenv`, `--project-directory` no compose | Sem dependência nova; `--project-directory` obrigaria a reescrever todos os caminhos do compose                 |
| `setup-dev.sh` move o `apps/backend/.env` antigo   | Pedir para cada um mover à mão                        | Quem já tinha o ambiente montado não perde as configurações                                                     |
| Frontend continua sem `.env`                       | `envDir` do Vite apontando para a raiz                | Hoje o front não usa variável nenhuma; se um dia usar, o Vite só expõe as `VITE_*`                              |

O `.dockerignore` já bloqueia `**/.env`, então o arquivo da raiz não entra nas imagens.

## Como testar

```bash
./infra/scripts/setup-dev.sh   # cria (ou move) o .env da raiz
pnpm dev                       # backend sobe lendo o .env da raiz
pnpm docker:dev                # compose usa POSTGRES_*, DB_PORT etc. do mesmo arquivo
```
