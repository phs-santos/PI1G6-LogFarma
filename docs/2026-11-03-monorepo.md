# Migração dos 4 repositórios para o monorepo

- **Implementado em:** 2026-11-03
- **Última alteração:** —
- **Requisitos:** RNF04 (facilita escalar e manter o sistema)

## Em poucas palavras

Antes o projeto era como quatro casas em ruas diferentes: para fazer uma feature, a gente andava de casa em casa (style-guide → backend → frontend), cada uma com a sua chave (SSH) e o seu carteiro (CI). Agora é **um prédio só com quatro apartamentos**: mesma portaria (um `pnpm install`), mesmo correio (um CI) e dá para subir de um andar para o outro pela escada interna — o frontend enxerga o style-guide na hora, sem publicar nada.

## O que

- Os repositórios `Grupo-PI-6/backend`, `frontend`, `style-guide` e `infra` foram unidos no repositório `PI1G6-LogFarma`, **com o histórico de commits de cada um preservado**.
- Um único workspace pnpm na raiz, com um único `pnpm-lock.yaml`.
- O frontend passou a usar o style-guide como `workspace:*` em vez de dependência git por SSH.
- Dockerfiles, `infra/compose.yaml`, scripts e workflows do GitHub adaptados ao novo layout.
- `CLAUDE.md`/`AGENTS.md` da raiz agora concentram o contexto do projeto e as **regras para agentes**; os de cada pacote ficaram só com o que é específico.
- Criada esta pasta `docs/`.

## Por que

- Uma feature que atravessava os três pacotes virava três PRs, em três repositórios, numa ordem obrigatória.
- O style-guide era privado e instalado por SSH: todo mundo (e o CI, e o build Docker) precisava de chave; mudanças só chegavam ao frontend depois de merge + `pnpm update`.
- Templates de issue/PR, `.editorconfig`, `CLAUDE.md` e contexto do projeto estavam copiados em 4 lugares e iam divergir.
- O `infra` dependia de os outros repos estarem clonados "ao lado" (`../backend`), o que quebrava com facilidade.

## Onde

```
PI1G6-LogFarma/
├── apps/
│   ├── backend/            ← era Grupo-PI-6/backend
│   └── frontend/           ← era Grupo-PI-6/frontend
├── packages/
│   └── style-guide/        ← era Grupo-PI-6/style-guide
├── infra/                  ← era Grupo-PI-6/infra
├── docs/                   ← novo
├── .github/                ← templates + workflows unificados
├── package.json            ← scripts do monorepo
├── pnpm-workspace.yaml
├── pnpm-lock.yaml          ← lockfile único
├── CLAUDE.md / AGENTS.md   ← contexto + regras para agentes
└── .dockerignore / .editorconfig / .gitignore
```

Arquivos alterados em cada pacote:

| Arquivo | Mudança |
|---|---|
| `apps/frontend/package.json` | `@fatec-pi/style-guide`: `git+ssh://…#main` → `workspace:*` |
| `apps/*/Dockerfile` | Contexto de build passa a ser a raiz; instala com `--filter`; sem SSH |
| `infra/compose.yaml` | `context: ..` + `dockerfile: apps/<app>/Dockerfile`; volumes novos; style-guide montado no container do frontend |
| `infra/compose.prod.yaml` | Imagens em `${IMAGE_PREFIX}/backend` e `/frontend` |
| `infra/scripts/setup-dev.sh` | Não clona mais nada; só cria os `.env` |
| `.github/workflows/ci.yml` | Um job para os 3 pacotes + um job para validar a infra |
| `.github/workflows/imagem-backend.yml` / `imagem-frontend.yml` | Publicam a imagem só quando a pasta do app (ou o style-guide, no caso do frontend) muda |
| `.github/workflows/deploy.yml` | Igual ao antigo, chamando `./infra/scripts/deploy.sh` |

## Escolhas feitas

| Escolha | Alternativas consideradas | Motivo |
|---|---|---|
| Layout `apps/` + `packages/` + `infra/` | Tudo na raiz (`backend/`, `frontend/`…) | Padrão de monorepo; separa o que é aplicação do que é biblioteca compartilhada |
| Preservar histórico (reescrevendo cada repo para a sua subpasta e unindo com merge) | Copiar os arquivos num commit novo | `git log -- apps/backend` continua mostrando quem fez o quê e quando |
| pnpm workspaces puro | Turborepo / Nx | Projeto pequeno; o `pnpm -r` já resolve. Dá para adicionar Turborepo depois, se o build ficar lento |
| Style-guide como `workspace:*`, exportando o código-fonte TS | Publicar em registry / continuar via git | Zero publicação, zero chave SSH, hot reload entre pacotes |
| Um `pnpm-lock.yaml` regenerado na raiz | Manter os 3 lockfiles | O pnpm só suporta um lockfile por workspace. As versões ficaram dentro das mesmas faixas do `package.json` |
| Contexto do Docker na raiz + `.dockerignore` único | Um contexto por app | O frontend precisa enxergar `packages/style-guide` durante o build |
| Imagens em `ghcr.io/<dono>/<repo>/{backend,frontend}` | Manter `ghcr.io/grupo-pi-6/*` | O `GITHUB_TOKEN` só publica no dono do repositório; o prefixo é configurável por `IMAGE_PREFIX` no `.env` da VPS |
| Pasta da VPS continua `~/grupo-pi-6` | Renomear | Não quebrar uma VPS que já esteja configurada |
| `.claude/`, `.agents/`, `.codex/` mantidos dentro de cada pacote | Juntar tudo na raiz | As skills (`nova-rota`, `nova-pagina`, `novo-componente`) são de cada pacote |

## Como testar

```bash
pnpm install
pnpm typecheck
pnpm build
pnpm docker:dev        # http://localhost:5173 e http://localhost:3333/api/health
```

Verificado em 2026-11-03: `typecheck` e `build` passando nos 3 pacotes; imagens `dev` e `prod` de backend e frontend construindo; stack de dev no Docker respondendo em `/api/health` direto e pelo proxy do frontend.

## Pendências

- Criar o environment `producao` e os secrets (`VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`) no repositório novo — ver `infra/README.md`.
- O secret `STYLE_GUIDE_DEPLOY_KEY` não é mais necessário.
- Decidir o que fazer com os 4 repositórios antigos da org `Grupo-PI-6` (arquivar com aviso apontando para cá).
